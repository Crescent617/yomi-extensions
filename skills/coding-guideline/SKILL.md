# Coding Guidelines

- Think first：不假设、不藏疑、不沉默地选边。拿不准就问；有多种理解就全摆出来；有更简单的做法就直说。
- KISS：只写解决问题所需的最少代码——不加功能、不加抽象、不防御不可能的场景。200 行能压成 50 行就重写。
- DRY：重复三次再抽象；两次就复制，别提前造轮子。
- Boy Scout Rule：离开代码时比来时干净一点——只清理你碰到的代码，不顺手重构无关部分。
- Test first：把任务翻译成可验证的目标，验证通过才算完成目标

## 判例（与五则同权，均出自真实 review/设计指令）

- 总目标「简单好用可靠」：没验证过的长尾功能直接砍，不留半成品分支。
- 错误处理不搞特殊：任何错都进同一条路径，统一语义单点收口；不特判豁免。
- 改就改干净：不加兼容层/过渡 shim，不做半吊子回摆；老语义要废就走迁移一次到位。
- 选择逻辑放服务端，先找现有传输面（请求 header、心跳 request-response）承载；不推给客户端，不为此改 proto。
- 装配处无分支：分支内收到中间件/函数内部，装配链保持直线；条件性组件返回 nil、末尾统一过滤。
- 定义与组装分开：哪里定义、哪里组装要说得清；输入与中间状态分结构体，字段多了先抽象一层，有业务聚类再细分。
- 同类项合并：重复的三连调用合一；强相关文件合一并以核心概念命名；新配置与既有配置放一处。
- 命名要语义准确：枚举归组用 isXxxFamily 谓词；字段放错层是设计瑕疵，该质疑 in/out 设计本身；拿不准的名字就问。
- 默认值沉进默认配置层，不改部署 yaml；依赖走既有 DI 注入，不新造结构体。
- 注释 ≤20 字，逐条说清，不重复，不为对齐加空格——文档的读者是模型。
- 定了 source of truth 就别看差异，直接替换。
- Secret 不落命令行明文、不进公开仓库；公网产物不带内部信息（内网域名、邮箱、内部地址）。
- 分支名禁用 `/`（go get、镜像 tag、app 名、域名都吃分支名）；小改动不叠 stacked MR，栈叠仅限大功能真依赖拆分。

## Adversarial Review

- 改动跨多文件或涉及核心行为时，交由 reviewer subagent 独立评审
- 评审立场是证伪而非确认。按优先级排查：正确性（边界/空值/并发/失败路径）→ 本 guideline → 代码库既有约定 → 测试覆盖。findings 按 blocker/nit 分级、标注代码位置；blocker 全部修复且测试通过才算完成。
- 评审方向是逼简：每轮先问「能否更少」——能删不加、能直说不绕、简化优先于分支化。
